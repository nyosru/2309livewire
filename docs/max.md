# MAX: прямое подключение и общий сервис

Интеграция обращается непосредственно к `https://platform-api2.max.ru`, без посредников. Она общая для всех сайтов этого Laravel-приложения. Отдельные приложения на сервере могут пользоваться защищённым JSON API.

## Что реализовано

- `App\Services\Max\MaxService`: отправка текста пользователю/чату и регистрация webhook.
- `App\Services\Max\RecipientRegistry`: проверенная привязка телефона к MAX ID.
- `App\Services\Max\MaxAuthService`: одноразовые коды, срок действия, лимиты, привязка к браузерной сессии и назначению.
- Вход в панель кафе через MAX, независимо от VK. Доступ выдаётся только по телефону; MAX ID определяется автоматически при подтверждении контакта в боте.
- Webhook при запуске бота предлагает кнопку «Поделиться телефоном», проверяет подпись контакта MAX и сохраняет привязку. Самостоятельно права не выдаёт; `/id` оставлен для диагностики.

## Ограничения прямого Bot API

В [POST /messages](https://dev.max.ru/docs-api/methods/POST/messages) получатель задаётся через `user_id` или `chat_id`, не телефон. Пользователь должен начать общение с ботом. Поэтому для входа по телефону сначала нужна доверенная привязка «телефон → MAX ID». Присланный боту чужой контакт не считается подтверждением владельца номера.

Пункт 1.5 [требований MAX](https://dev.max.ru/docs/legal/requirements) предусматривает отправку авторизационных сообщений через техническую интеграцию в случаях, оговорённых договором с MAX. Само создание бота ещё не подтверждает подключение этого вида сообщений. Поэтому доставка кодов по умолчанию выключена (`MAX_AUTH_DRIVER=disabled`).

У MAX есть отдельный чат [«Коды авторизации»](https://max.ru/code) для сообщений сторонних сервисов по номеру телефона. Для прямого подключения этого продукта нужно запросить у MAX условия, доступ и документацию его API, в том числе параметры отправителя, доставки и проверки кода. Такой API здесь не имитируется: интеграция использует только публично документированный Bot API. Сторонние провайдеры не подключены.

## Хранение и редактирование настроек

Бот настраивается суперадминистратором в `/admin/settings`: имя, токен, включение входа, адрес и секрет получения событий. Общая настройка MAX действует для всех проектов, использующих этот бот.

Миграция `2026_10_23_000006_create_application_settings_table.php` однократно копирует текущие `config/max.php` / `.env` в `application_settings` (строка `max`). Далее `App\Services\Max\MaxSettings` читает только БД: изменение старых env-переменных или `config:cache` не меняет бота. Пустые поля нового токена и секрета сохраняют старые значения. Секреты зашифрованы ключом Laravel `APP_KEY`, не показываются в HTML и не записываются в old input. Для переноса/восстановления БД нужен тот же `APP_KEY`.

Серверные настройки `MAX_CA_BUNDLE`, `MAX_AUTH_SERVICE_CLIENTS`, лимиты кодов и учётные записи суперадминистратора остаются в серверной конфигурации. При изменении адреса или секрета webhook после сохранения повторно выполнить `max:register-webhook`: команда читает данные из БД. Сохранение формы само не меняет подписку у MAX.

## Исходные настройки перед первой миграцией

Получить в настройках уже созданного бота на платформе MAX:

```dotenv
MAX_BOT_TOKEN=
MAX_CA_BUNDLE=resources/certs/max-russian-trusted-root.pem
MAX_BOT_USERNAME=
MAX_WEBHOOK_SECRET=
MAX_WEBHOOK_URL=https://your-domain.example/api/max/webhook
MAX_AUTH_DRIVER=disabled
VKUSNO_SUPER_ADMIN_PHONE=+79XXXXXXXXX
MAX_AUTH_SERVICE_CLIENTS={}
```

- `MAX_BOT_TOKEN`: токен бота. Секрет, хранить только на сервере.
- `MAX_CA_BUNDLE`: отдельный PEM-файл корневого сертификата для соединений с MAX. В репозитории есть сертификат, полученный с официального HTTPS-ресурса Госуслуг; источник и отпечаток — в `resources/certs/README.md`. Применяется только к фиксированному API MAX, системное хранилище доверия не меняется. Если параметр пуст, используется системная проверка TLS. Проверка имени узла включена в обоих режимах. Не отключать её при ошибке сертификата.
- `MAX_BOT_USERNAME`: никнейм из ссылки `https://max.ru/<никнейм>`, без `@`.
- `MAX_WEBHOOK_SECRET`: придумать случайную строку 32–64 символа из букв, цифр, `_`, `-`; не совпадает с токеном бота. Можно сгенерировать `openssl rand -hex 32`.
- `MAX_WEBHOOK_URL`: публичный HTTPS-адрес обработчика. Для кафе: `https://xn--72-dlcyjau5ar6c5d.xn--p1ai/api/max/webhook`. Сервер слушает 443, сертификат доверенный. Локальный домен и самоподписанный сертификат не принимаются MAX.
- `MAX_AUTH_DRIVER=bot`: включить прямую доставку кодов своим ботом после подключения соответствующего сценария у MAX.
- `VKUSNO_SUPER_ADMIN_PHONE`: нормализованный телефон суперадминистратора кафе; фактический номер хранится в локальной `.env`, не в этом документе.
- `MAX_AUTH_SERVICE_CLIENTS`: необязательный JSON с отдельным случайным ключом для каждого внешнего серверного приложения. Пустой объект закрывает доступ к серверному API.

После настройки:

```bash
docker exec 2309livewire php artisan migrate --path=database/migrations/2026_10_22_000005_create_max_auth_tables.php --force
docker exec 2309livewire php artisan migrate --path=database/migrations/2026_10_23_000006_create_application_settings_table.php --force
docker exec 2309livewire php artisan config:clear
docker exec 2309livewire php artisan max:register-webhook
```

Команда webhook отправляет подписку на `bot_started` и `message_created` с секретом. Проверка заголовка `X-Max-Bot-Api-Secret` соответствует [документации подписок MAX](https://dev.max.ru/docs-api/methods/POST/subscriptions). Регистрация и сообщения не выполняются автоматически при развёртывании или тестах.

## Первый вход без VK

1. Пользователь открывает бота по ссылке или QR-коду на `/admin/login` и нажимает «Начать».
2. Бот предлагает «Поделиться телефоном». Пользователь нажимает именно эту кнопку, а не отправляет контакт через скрепку.
3. Webhook проверяет HMAC-SHA256 подпись `vcf_info` токеном бота, совпадение `max_info.user_id` с отправителем и личный диалог. Пересланные сообщения, неподписанные контакты и конфликтующие привязки отклоняются. Привязка сохраняется автоматически, MAX ID вручную не нужен. Формат — в [документации MAX](https://dev.max.ru/docs-api/use-cases/sending-messages/keyboard).
4. Для первого входа суперадминистратора достаточно номера `VKUSNO_SUPER_ADMIN_PHONE` и правильного одноразового кода. Первый случайный посетитель суперадминистратором не становится. Запуск бота сам по себе прав не выдаёт.
5. Остальным суперадминистратор разрешает вход в `/admin/access`, указав только телефон. Разрешение можно выдать до подтверждения контакта.
6. Пользователь возвращается на `/admin/login`, вводит телефон, получает код в MAX и вводит его на сайте. Аккаунт VK не требуется.

Без работающего публичного webhook кнопка и автоматическая привязка не работают. После развёртывания обработчика зарегистрировать webhook, затем повторно отправить боту `/start`.

Резервная серверная выдача разрешения по телефону:

```bash
docker exec 2309livewire php artisan vkusno:max-admin '+79XXXXXXXXX' --name='Администратор'
```

Команда не подтверждает телефон и не отправляет сообщений. Пользователь всё равно должен поделиться подписанным контактом в боте. Необязательный второй аргумент MAX ID оставлен только для доверенного ручного восстановления привязки.

## Использование в другом сайте этого Laravel-приложения

```php
use App\Services\Max\MaxService;
use App\Services\Max\MaxAuthService;
use App\Services\Max\RecipientRegistry;
use Illuminate\Support\Str;

// Только в доверенной административной операции, после проверки пары человеком.
app(RecipientRegistry::class)->register('+79120000000', '123456789');

app(MaxService::class)->sendToUser('123456789', 'Текст сообщения');
// Для группового чата — sendToChat($chatId, $text).

$context = session('other_site.max_context', Str::random(64));
session(['other_site.max_context' => $context]);
$verification = app(MaxAuthService::class)->begin(
    '+79120000000', 'other-site.login', $context, request()->ip(), true, 'Другой сайт'
);
session(['other_site.max_verification' => $verification->id]);

// В отдельном POST после ввода кода, с тем же контекстом из сессии:
$phone = app(MaxAuthService::class)->confirm(
    session('other_site.max_verification'), 'other-site.login', $context, request('max_code')
);
if ($phone !== null) {
    // Проверить разрешения на этот сайт. Только затем выполнить его вход.
    // Ротация session ID, удаление контекста и запрет повторного использования обязательны.
}
```

Не использовать один purpose для разных сайтов. Не принимать purpose и browser context непосредственно от браузера. Одноразовый код не логировать, не возвращать в HTML/JSON и не сохранять в old input. HTTP-ошибки и ограничение частоты обрабатывает вызывающий сайт. Автоматический повтор отправки запрещён: он может породить дубликаты.

## Отдельные проекты на том же сервере: HTTP API

Задать ключи, например (заменить пример настоящим случайным секретом):

```dotenv
MAX_AUTH_SERVICE_CLIENTS='{"project-a":"random-server-secret-at-least-32-characters"}'
```

Для всех запросов передавать заголовки:

```text
Content-Type: application/json
Accept: application/json
X-Max-Service-Client: project-a
X-Max-Service-Key: <секрет проекта>
```

Запросы выполнять только с доверенного сервера по HTTPS. Ключи в JavaScript браузера не размещать.

### Уведомление

`POST /api/max/service/message`

```json
{"user_id":"123456789","text":"Текст сообщения"}
```

Для чата передать `chat_id` вместо `user_id`. Вместе их передавать нельзя. Успех: `{"sent":true}`. Максимум 4000 символов. В вызывающем проекте учитывать ограничения MAX: до 2 сообщений в секунду на получателя и до 30 запросов в секунду на бота; при ошибке организовать контролируемую очередь, не бесконечные повторы.

### Запрос кода

`POST /api/max/service/auth/start`

```json
{"phone":"+79120000000","context":"random-64-character-session-token-created-by-your-backend","label":"Название проекта"}
```

`context` создаёт сервер вызывающего проекта для конкретной браузерной сессии. Телефон должен иметь доверенную привязку в общей базе. Сервис сам задаёт purpose `service.<имя клиента>`; изменить его параметром запроса нельзя. Перед вызовом проверить, разрешён ли этому телефону вход на конкретный сайт.

Ответ `201` содержит `verification_id`, `code_length`, `expires_at`. Сохранить ID в серверной сессии своего проекта, показать пользователю поле для кода. Поставщик не раскрывается пользователю, код не возвращается API.

### Проверка кода

`POST /api/max/service/auth/check`

```json
{"verification_id":"UUID-из-start","context":"тот-же-сессионный-токен","code":"123456"}
```

Успех `200`: `{"verified":true,"phone":"+79120000000"}`. Это доказательство владения привязанным аккаунтом MAX, а не автоматическое разрешение доступа к любому проекту. Проверить собственный список разрешённых пользователей и только затем выполнить вход.

Другой клиент сервиса не может подтвердить эту проверку. Повторное использование, неверный контекст, истечение срока и неверный код возвращают `422`. Без ключа/с неправильным ключом — `403`, при превышении частоты — `429`, при недоступности доставки — ошибка без секретов.

## Проверки

```bash
docker exec 2309livewire php artisan test --compact tests/Feature/Vkusno
```

`MaxAuthTest` подменяет HTTP-ответы MAX. Покрыты одноразовость, хеши, истечение срока, попытки, повторная отправка, отсутствие VK, суперадминистратор по телефону, отзыв прав, webhook, серверные клиенты и команды. Рабочие номера и токены в тестах не используются.
